# Tremor-stabilizing gimbal simulation prototype

The repository contains three CAD STEP assemblies, static MuJoCo visual
previews, and a working two-axis spoon gimbal simulation. The first experiment
uses a prescribed handle motion, an upright-axis task, analytic joint mapping,
and ideal torque control with provisional inertial parameters. A second
experiment follows voluntary handle orientation while estimating and removing
a prescribed tremor component with a simplified WFLC. A third experiment
balances upright orientation against fixed spoon-tip position.

Earlier MuJoCo/WFLC output files and reports have been removed. Historical
experiment descriptions below remain for context; their scripts regenerate
those outputs when run. Current signal-benchmark results are under
`reports/tremor_baselines/` and `experiments/results/tremor_baselines/`.

## Run the first working prototype

Use Python 3.11 with MuJoCo 3.10.0, NumPy 2.4.6, and Matplotlib 3.11.2. These
versions are installed in the local `me5418` environment; `requirements.txt`
records them for a fresh environment.

```bash
conda activate me5418
python -m gimbal.experiment --all
python scripts/check_gimbal_model.py
python scripts/check_stabilization.py
```

`--all` runs the stationary and oscillatory handle cases with torque off and
with PD control. It saves CSV logs, PNG plots, and JSON metrics in
`experiments/results/`. To watch the moving controlled gimbal, run:

```bash
python -m gimbal.experiment --scenario oscillatory --controller pd --view --duration 20
```

The viewer needs a desktop OpenGL display. Headless simulation and plot export
were checked here; interactive viewing is intended for the user's desktop.

## Moving two-axis spoon model

`models/gimbal_spoon.xml` is the plant prepared for control development. It
has a kinematically driven handle (`mocap` body), two hinge joints (`roll`,
`pitch`), 16 visual CAD meshes, two ideal joint-torque motors, and named
ground-truth pose and joint sensors. Mesh collisions are disabled. The MJCF
has no embedded controller; `gimbal/experiment.py` drives its torque inputs.
Motor electronics and contact with a table or food are not modeled in this
original spoon stabilization scene. Separate simplified contact scenes for the
lock mode are described below.

The neutral CAD/world frame is right-handed: X runs along the handle toward
the spoon, Y runs across the fork, and Z completes the frame. The roll axis is
CAD +X through `(6.02, 0, 0)` mm, measured from the `rm_shaft` cylindrical
surface. The pitch axis is CAD +Y through `(73, 0, 0)` mm, measured from
`pm_shaft`. The implemented orientation convention is

`R_tool_world = R_handle_world * R_x(q_roll) * R_y(q_pitch)`.

At the neutral pose the original CAD coordinates are preserved. The handle
contains `h_upper` and `h_lower`. The roll frame contains the symmetric U
covers, fork, counterweight, and pitch covers. The pitch frame contains the
shaft, quick release, spoon holder, adapters, mounts, and spoon head. This is
a practical first rigid-body grouping inferred from part names and placement;
the STEP package has no original SolidWorks mates to confirm every assignment.

The chosen moving-body masses are **assumptions**, not CAD material results:
0.11 kg for the roll frame and 0.06 kg for the pitch/tool frame. Their centers
of mass and full inertia tensors come from selected STEP solid volumes under a
uniform-density assumption, scaled to those masses. Joint ranges are
provisionally ±45 degrees, torque control ranges ±0.15 N m, and simulation
timestep is 0.001 s with the `implicitfast` integrator. Actual hardware limits,
motor torque, damping, and mass distribution should replace these assumptions
when available.

Set `data.mocap_pos[0]` and `data.mocap_quat[0]` to prescribe the handle pose;
write desired torques to `data.ctrl[0:2]`. The frame quaternion and joint
sensors are ideal simulator ground truth. The `tool_frame` site follows the
pitch frame, and `spoon_tip` marks a point near the utensil end.

Run the model checks with:


The current check passes in MuJoCo 3.10.0: all 16 neutral meshes align with
their source STL bounding boxes within 1.1e-8 m; analytical frame composition
and tip position agree with MuJoCo; positive torque turns each joint in its

## Open-loop baseline before control

From the repository root, run a prescribed 2 Hz handle roll (0.10 rad) and
1.5 Hz handle pitch (0.05 rad) with **zero joint torque**:

```bash
conda activate me5418
python scripts/run_open_loop.py --mode oscillatory --duration 5
```

Use `--mode stationary` for a fixed handle. Add `--view` to watch the run in
the MuJoCo window; for example, `python scripts/run_open_loop.py --view
--duration 20`. The script saves a CSV and PNG under `experiments/results/`.
It samples at 100 Hz while MuJoCo steps at 1 kHz. The measured task error is
the angle between the tool frame's +Z axis and world +Z, a simple upright-axis
reference. Joint positions, handle motion, tool error, and actual actuator
torques are recorded. The handle trajectory is deterministic, with no noise or
random seed. This is a baseline, not stabilization: gravity drives the free
joints toward their provisional limits.

In a 2 s checked run, the stationary and oscillatory cases each produced 200
samples. Their tool-axis error RMS values were 50.70 and 50.67 degrees,
respectively. These values describe the unpowered mechanism under the stated
provisional mass and damping assumptions; they are not suppression results.

## Fixed-axis stabilization experiment

The task target is **tool frame +Z aligned with world +Z**. The neutral spoon
CAD frame defines this tool axis; it is a geometry reference, not a claim about
spill prevention. The two joints do not control yaw or spoon-tip position.
`gimbal/kinematics.py` implements the verified frame order
`R_world_tool = R_world_handle Rx(q_roll) Ry(q_pitch)`. For the target axis,
it computes the corresponding roll and pitch from
`R_world_handle.T @ [0, 0, 1]`. The principal IK branch is used near upright.
Requests beyond the provisional ±45 degree joint limits are clipped, marked
unreachable, and given a nonzero residual; the clipping is not claimed to be
an optimal projection.

`gimbal/motion.py` prescribes the handle, and `gimbal/control.py` supplies a
joint PD law with MuJoCo bias-force compensation and explicit ±0.15 N m torque
clipping. The control law is
`tau = clip(Kp (q_des - q) - Kd qdot + qfrc_bias)` with
`Kp = 0.6 N m/rad` and `Kd = 0.002 N m s/rad` on each joint. Desired joint
velocity is zero. This uses simulator ground-truth handle orientation, joint
states, and bias force; there is no IMU, encoder noise, or estimator yet.

The experiment runs MuJoCo's `implicitfast` integrator at 1 ms, updates control
at 1 ms, and logs at 10 ms. The moving handle follows a 0.10 rad, 2 Hz roll
and 0.05 rad, 1.5 Hz pitch. The stationary tracking case starts with joint
angles `(0.2, -0.15)` rad and targets upright. The experiment has no random
inputs or random seed. Each CSV records handle motion, desired and actual joint
angles, desired and actual tool-axis components, axis and joint errors,
actuator torques, saturation, and IK reachability. Metrics use samples from
1 s onward for the default 5 s run. Attenuation is
`1 - RMS(tool-axis error) / RMS(handle-axis error)`; it is undefined for the
stationary handle.

Validated 5 s results in MuJoCo 3.10.0:

| Handle | Control | Tool-axis RMS | Peak torque | Saturated control updates |
| --- | --- | ---: | ---: | ---: |
| Stationary | Off | 53.53° | 0 N m | 0% |
| Stationary | PD | 0.02° | 0.123 N m | 0% |
| Oscillatory | Off | 53.77° | 0 N m | 0% |
| Oscillatory | PD | 0.66° | 0.021 N m | 0% |

In the oscillatory PD run, handle-axis RMS was 4.52°, giving 85.3% axis-error
attenuation under this specific simulated input. Joint tracking RMS was 0.45°.
The unpowered tool error is dominated by gravity-driven joint motion, so the
PD-versus-off comparison does not isolate tremor suppression. This first task
does not test intentional movement preservation, tool-tip position, contact,
sensor imperfections, motor dynamics, or clinical benefit.

## Voluntary-motion following with WFLC

Run the follow-mode comparison and its checks from the repository root:

```bash
conda activate me5418
python -m gimbal.follow --all
python scripts/check_follow.py
```

Watch the WFLC-controlled gimbal on a desktop with OpenGL:

```bash
python -m gimbal.follow --scenario mixed --estimator wflc --view --duration 20
```

`gimbal/motion.py` prescribes a slow voluntary roll (0.12 rad at 0.25 Hz) and
pitch (0.08 rad at 0.18 Hz), plus a 5.2 Hz one-harmonic tremor (0.06 rad roll,
0.04 rad pitch) ramped over 0.5 s. These are **synthetic test assumptions**.
Only the combined handle pose reaches the estimator. The separate components
are logged for evaluation, not read by the WFLC or controller. Handle pose and
joint state are still MuJoCo ground truth; there is no measurement noise.

The task target is the world-frame +Z axis of the *estimated voluntary* RxRy
orientation. `gimbal/kinematics.py` maps this target axis and current measured
handle orientation to joint references. Yaw and tool-tip position remain
uncontrolled. Three selectable estimators provide the target:

- `passthrough`: follow the measured handle orientation directly;
- `lowpass`: causal first-order 1.5 Hz low-pass on handle angles;
- `wflc`: one-harmonic, two-axis WFLC frequency tracker on causally
  high-passed angles, followed by an adaptive Fourier amplitude model on the
  raw angles. The raw-signal model supplies the tremor estimate subtracted
  from measured angles.

The [Riviere et al. WFLC study](https://www.ri.cmu.edu/pub_files/pub3/riviere_cameron_1998_1/riviere_cameron_1998_1.pdf)
motivates this two-stage frequency-estimation and raw-signal cancellation
structure. This code is a small discrete implementation for simulated angular
motion, **not a reproduction of that paper's hardware or tuned filter**.
The high-pass cutoff is 2 Hz. The WFLC starts at 4.5 Hz and is constrained to
3–8 Hz; these are configurable in `gimbal/estimators.py`. Its one-harmonic
model will not generally represent multiple tremor frequencies, abrupt
frequency changes, or voluntary movement in the same frequency band.

The joint servo uses the same PD plus bias-force form as the upright experiment,
but gains of `Kp = 5 N m/rad` and `Kd = 0.008 N m s/rad` to track this faster
reference. Torque remains limited to ±0.15 N m. MuJoCo and control update at
1 ms; CSV samples are logged every 10 ms. The default run is 12 s, with RMS
metrics evaluated after 3 s so the WFLC startup is reported separately in the
plots. `follow_mixed_*.csv`, PNG, and JSON files under `experiments/results/`
include measured motion, true components for evaluation, estimated intent and
tremor, estimated frequency, joint tracking, tool-axis errors, torques,
saturation, and IK reachability.

Validated default-run results (tool-axis error relative to the true voluntary
target; degrees RMS after 3 s):

| Estimator | Voluntary + tremor | Voluntary only |
| --- | ---: | ---: |
| Direct follow | 2.92° | 0.00° |
| Low-pass | 1.09° | 0.88° |
| WFLC | 0.71° | 0.02° |

For the mixed WFLC run, the handle-to-voluntary error was 2.92° RMS, reference
error was 0.50° RMS, and tool-to-reference servo error was 0.32° RMS. The
resulting 0.71° tool error is a 75.7% reduction relative to direct following
under this single synthetic scenario. The final WFLC frequency estimate was
5.13 Hz versus the prescribed 5.2 Hz; peak commanded torque was 0.034 N m,
with no saturation or unreachable IK commands. In the voluntary-only case,
the frequency output has no physical tremor to identify and should not be
interpreted. These results do not establish performance on real tremor,
noisy IMUs, multiple oscillation frequencies, or actual hardware.

## Weighted spoon-tip position and orientation stabilization

Run the five-weight comparison and geometry/control checks:

```bash
conda activate me5418
python -m gimbal.position_experiment --all
python scripts/check_position_task.py
```

Watch one setting in the MuJoCo viewer:

```bash
python -m gimbal.position_experiment --scenario moving --weight 0.5 --view --duration 20
```

The purple world marker is the fixed spoon-tip target at `(0.154, 0, 0)` m,
the neutral tip location. The orientation target remains world +Z for the tool
frame's +Z axis. The moving handle has prescribed translations of 6 mm in X,
4 mm in Y, and 8 mm in Z at 0.7, 0.9, and 1.1 Hz, plus roll 0.08 rad at
1.7 Hz and pitch 0.05 rad at 1.3 Hz. The stationary case is a zero-motion
sanity check. These trajectories are synthetic tests, not measured tremor.
This fixed-reference experiment uses MuJoCo ground-truth handle pose and does
not run the WFLC follow estimator; it isolates the two-DoF position/orientation
tradeoff.

`gimbal/task_ik.py` uses the verified spoon-tip FK and analytic 3-by-2
Jacobians to solve a bounded, damped Gauss-Newton problem. For orientation
weight `w` in `[0, 1]`, the objective is

`w ||tool_axis - world_Z||² + (1-w) ||tip_position - target_position||² / (0.15 m)²`.

The axis-vector difference is a chord error; reported orientation results use
the actual angle in degrees. The 0.15 m scale makes position and orientation
terms dimensionless and is part of the task definition. Joint limits remain
±45°. The applied joint reference is additionally restricted to change by at
most 1.5 rad/s per joint, which avoids jumps between nearly equivalent
position-only IK solutions. The controller is PD plus MuJoCo bias compensation
with `Kp = 1.5 N m/rad`, `Kd = 0.004 N m s/rad`, and ±0.15 N m torque limits.
MuJoCo and torque control step at 1 ms; the IK reference and CSV log update
at 10 ms. `--weight` and `--reference-rate` expose the two user-adjustable
parameters. The IK is local and task constrained; it does not claim that both
targets are exactly reachable.

Validated moving-handle results for 5 s runs, measured after the first second:

| Orientation weight `w` | Tool-axis RMS error | Tip-position RMS error | Torque saturation |
| ---: | ---: | ---: | ---: |
| 0.00 | 22.85° | 5.21 mm | 0% |
| 0.25 | 2.24° | 6.23 mm | 0% |
| 0.50 | 1.14° | 7.26 mm | 0% |
| 0.75 | 0.56° | 7.93 mm | 0% |
| 1.00 | 0.35° | 8.38 mm | 0% |

The sweep plot is `experiments/results/position_weight_tradeoff.png`. Each
weight also has a CSV, PNG, and JSON file named `position_moving_w*.{csv,png,json}`.
For a geometric `q=0` rigid-tool comparison under the same base trajectory,
the tip error is 9.94 mm RMS and the axis error is 3.83° RMS; this comparison
does not include passive joint dynamics. The `w=0.25` setting improves both
metrics relative to that rigid reference in this scenario.
At `w=0`, the position task has weak roll authority near the neutral spoon
geometry: the target reaches a joint limit in 4.4% of IK updates, and the
tool may tilt substantially to move the tip. At `w=1`, tip translation is
largely unconstrained. The nonzero residuals explicitly show the two-DoF
mechanism's limits; neither position nor orientation numbers imply spill
prevention or full six-DoF stabilization.

## Interaction lock mode: key, spoon, and cup

Build the three dynamic CAD-visualized interaction models and run all demos:

```bash
conda activate me5418
python scripts/build_lock_models.py
python -m gimbal.lock --task all
python scripts/check_lock.py
```

Watch one scene with the MuJoCo viewer (the small tool contact proxy changes
from blue to orange while locked):

```bash
python -m gimbal.lock --task key --view
python -m gimbal.lock --task spoon --view
python -m gimbal.lock --task cup --view
```

`--mode free` runs the same scene with continuous world-upright stabilization
for comparison. Outputs are `experiments/results/lock_{key,spoon,cup}_{auto,free}`
CSV, PNG, and JSON files. The default run lasts 3.4 s: the prescribed handle
approaches, dwells, then retracts. Base roll and pitch are also prescribed;
the cup scene omits base pitch to avoid driving its rigid cup through the
table. The moving base is not stopped by contact, so the normal forces are
specific to this idealized trajectory and compliance.

The lock is **a soft joint-angle hold**, not a mechanical latch. Before the
event, the existing upright-axis IK supplies the reference. At first event,
the controller captures the current two joint angles and holds them with the
same saturated PD-plus-bias torque servo. After retraction, it returns to
upright stabilization. For spoon and cup, the event is a MuJoCo contact
between their tool proxy and a fixed spherical mouth surrogate or table;
release requires 40 ms without contact during retraction. For the key, entry
is detected when its tip crosses the plane of a rectangular clearance slot
while inside its opening. It releases after the tip retracts 3 mm past that
plane. Key entry can occur without wall contact, so its trigger uses tip
position, not a contact force. The key slot, mouth sphere, cup bottom point,
and table are deliberately simple task proxies.

The models use the same X-along-handle, roll-X then pitch-Y frames as the
spoon model. STEP-derived meshes are visual only. `build_lock_models.py`
groups their parts into moving bodies by product name and adds approximate
tool collision shapes. Roll mass/inertia is copied from the first spoon
prototype; tool masses are assumed to be 0.055 kg (key), 0.06 kg (spoon),
and 0.18 kg (cup), with provisional diagonal tool inertias. These properties,
contact compliance, target dimensions, and tool proxy placement are not
measurements of manufactured parts or human tissue. The 1 ms MuJoCo/control
step and 10 ms log step remain unchanged; joint torque is limited to
±0.15 N m. Contact force is logged from MuJoCo's contact solver, but is not
used as a safety limit. The controller does not stabilize world position
while locked; the tool moves with the handle subject to joint tracking error.

Verified 3.4 s default runs (one deterministic run per task):

| Task | Lock interval | Joint variation while locked vs free, 1.35–2.0 s | Peak simulated target contact force | Torque saturation |
| --- | ---: | ---: | ---: | ---: |
| Key entry | 0.742–2.824 s | 0.91° vs 1.64° | 1.0 N | 0% |
| Spoon to mouth proxy | 1.201–2.241 s | 0.11° vs 1.42° | 7.8 N | 0% |
| Cup to table proxy | 1.270–2.169 s | 0.05° vs 0.63° | 17.3 N | 0% |

The joint variation metric is the Euclidean norm of the two joint-angle
standard deviations in the stated interval. The simulated forces must not
be interpreted as safe contact forces for a person. A real contact mode would
need calibrated sensing, force limits, compliant hardware, and tests of
unexpected contact and release behavior.

The source bowl is 61 mm across (about 55 mm inside), with a 6 mm rim above the
floor at world Z=104 mm. The modestly wider opening fits the 48 × 36 mm spoon
bowl without trapping it between the rims. The source contains **180 independent
4 mm grains** (36.9 mg each), placed randomly without overlap and settled under
gravity for 1.6 s. Temporary forming walls are disabled before the visible task.
The table starts at X=95 mm so the bulky handle stays in front of its edge.

center to 0.3 mm at the lip, represented by 24 convex collision patches.

tolerance, overdamped contacts `solref="-100000 -900"`,
`solimp="0.90 0.98 0.0005"`, and 0.1 mm margins. Grain/container friction is 0.6;
spoon friction is 0.2 with higher material priority, representing a smoother
utensil. Three-dimensional contacts avoid unnecessary spin/rolling constraints.
Bodies remain rigid and contact compliance is an engineering approximation,
not measured food elasticity. The same two gimbal torque actuators and ±0.15 Nm
limits are used, with PD gains Kp=[5,5], Kd=[0.095,0.027]. Damping follows the
neutral inertia estimate and `2*sqrt(Kp*I)` rather than estimator-specific tuning.

**Motion-drive correction:** directly changing a mocap handle pose gives zero
handle velocity to MuJoCo's contact model. A legacy transport probe commanded
about 0.146 m/s while the simulator reported zero. The corrected viewer instead
welds a real dynamic handle to an independent mocap target (weld solref 0.002/1,
torque scale 1). Actual contact velocities are now available, with measured
transport velocity errors below 0.000265 m/s. This follows the
[official MoCap modeling recommendation](https://mujoco.readthedocs.io/en/stable/modeling.html#mocap-bodies).
Historical direct-mocap system task results must be rerun with the corrected
drive before supporting physical estimator rankings; signal-only results are
unaffected. Legacy Phase 2A viewer replay retains its original kinematic model
and displays archived states rather than running the corrected dynamics.

In 10 **no-tremor** checks (seeds 0–9), each run picked up **23–30 grains**
(mean 25.7, sample SD 1.9). All **257/257 picked grains** were retained through
transport and delivered to the target. The 100% ratio is conditional on the
lifted serving, not on all 180 source grains; source pickup fraction averages
14.3%. Raw pickup/delivery counts remain essential alongside percentages.
No sampled spoon/source penetration or torque saturation was detected. Maximum
sampled horizontal/upward grain speeds during scooping were 0.234/0.146 m/s.
These are observations, not imposed speed limits. The 21 s simulation including
settling took roughly 25.5–26.9 s without rendering on this machine, so strict

The native viewer requires a desktop display with OpenGL.

## Corrected dynamic-handle scoop algorithm comparison

The physical scoop scene now uses a dynamic handle welded to the mocap drive,
so contacts see the moving spoon's actual velocity. The new comparison keeps
all five estimator implementations and their Phase-2A calibration parameters
frozen. It evaluates the current 21 s, 180-source-grain scoop task; it does not
overwrite the historical preloaded-spoon results or repeat unaffected
signal-only experiments.

```bash
conda activate me5418
OPENBLAS_NUM_THREADS=1 python -m gimbal.system_benchmark_corrected --mode run --alpha 2 --workers 4
```

separates pickup count, delivered count, and conditional transport retention.

## Shallow-spoon transport sensitivity diagnostic

A separate 4 mm spoon variant is now available; original 8 mm replay files
retain their own geometry. Exploratory tests found that shallowing alone
(4 or 2 mm) still saturated transport retention at the old disturbance scale.
The new diagnostic therefore completes a common undisturbed scoop first,
then ramps tremor in over 0.5 s from the 11.2 s pickup checkpoint and enables
compensation identically for all methods. This isolates transport with matched
initial grain positions and picked particle IDs; it is separate from the
always-on-tremor scoop task.

```bash
OPENBLAS_NUM_THREADS=1 python -m gimbal.system_benchmark_corrected --mode run --alpha 5 --bowl-depth-mm 4 --transport-tremor-only --methods NoComp Oracle ABPF --seeds 10 --workers 4
```

The [sensitivity report](reports/system_benchmark/geometry_sensitivity/浅勺与等装载运输诊断报告.md)
records the development seeds (0–2), untouched validation seeds (3–9),
NoComp/Oracle-only condition selection, and native replay commands. Results
are grouped under `experiments/results/system_benchmark/geometry_sensitivity/`.
The viewer reads saved bowl depth automatically with `--replay-run`; live
geometry demonstrations also accept `--bowl-depth-mm 4`.
